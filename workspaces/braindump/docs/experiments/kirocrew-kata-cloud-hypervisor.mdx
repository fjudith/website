# Isolating kirocrew with Kata Containers + Cloud Hypervisor

:::info[Experiment log]
This is a write-up of my own setup for running **kirocrew** agents inside
hardware-isolated micro-VMs. Values that are specific to my environment are
called out as `PLACEHOLDER` — substitute your own. The mechanics (runtime
handlers, config paths, RuntimeClass) are the standard Kata Containers flow.
:::

## Why

kirocrew agents execute untrusted-ish work: they run tools, shell out, and
touch the filesystem on my behalf. Standard containers share the host kernel,
so a container escape is a host compromise. I wanted a stronger boundary
without changing how the agents are packaged or scheduled.

[Kata Containers](https://katacontainers.io) runs each pod inside a lightweight
VM with its **own guest kernel**, so a workload sees a real virtualization
boundary while still behaving like an OCI container. Paired with
[Cloud Hypervisor](https://www.cloudhypervisor.org) — a modern, Rust-based VMM
built for cloud workloads — the per-pod VM boots fast and stays lean.

## The pieces

| Component                    | Role                                                  |
| ---------------------------- | ----------------------------------------------------- |
| **Kata Containers**          | OCI-compatible runtime that launches each pod in a VM |
| **Cloud Hypervisor** (`clh`) | The VMM that runs the micro-VM                        |
| **containerd**               | Registers Kata as a runtime handler                   |
| **Kubernetes RuntimeClass**  | Selects the Kata+clh handler per workload             |
| **kirocrew**                 | The agent workload being isolated                     |

Kata supports several hypervisors (QEMU, Firecracker, Cloud Hypervisor, Dragonball).
This experiment uses **Cloud Hypervisor** because it supports device hotplug and
memory/CPU resizing that Firecracker does not, while staying much lighter than
QEMU.

## 1. Install Kata Containers

The static tarball is the least surprising install — it drops everything under
`/opt/kata` and does not fight your distro packages.

```bash
# Pick a release; check https://github.com/kata-containers/kata-containers/releases
KATA_VERSION="PLACEHOLDER"   # e.g. 3.x.y
curl -fsSL -o kata-static.tar.xz \
  "https://github.com/kata-containers/kata-containers/releases/download/${KATA_VERSION}/kata-static-${KATA_VERSION}-amd64.tar.xz"
sudo tar -xf kata-static.tar.xz -C /

# The Cloud Hypervisor binary ships in the tarball:
/opt/kata/bin/cloud-hypervisor --version
```

Confirm the host can actually do hardware virtualization:

```bash
kata-runtime check   # or: /opt/kata/bin/kata-runtime check
```

## 2. Point Kata at Cloud Hypervisor

Kata ships a per-hypervisor config. The Cloud Hypervisor one is
`configuration-clh.toml`:

```bash
sudo mkdir -p /etc/kata-containers
sudo cp /opt/kata/share/defaults/kata-containers/configuration-clh.toml \
        /etc/kata-containers/
```

The settings I tune for kirocrew (each agent VM is small and short-lived):

```toml
# /etc/kata-containers/configuration-clh.toml
[hypervisor.clh]
path = "/opt/kata/bin/cloud-hypervisor"
# Baseline resources per agent VM — override per workload via annotations.
default_vcpus = 1
default_memory = 512          # MiB
# Allow the VM to grow if a task needs it.
default_maxvcpus = 4
memory_slots = 10

[runtime]
# Handy while experimenting; drop for production.
enable_debug = true
```

:::tip
Per-pod overrides beat editing the global config. Kata reads annotations like
`io.katacontainers.config.hypervisor.default_memory`, so a heavy kirocrew task
can request more RAM without changing the default for every agent. You must
allowlist those annotations in the config's `enable_annotations`.
:::

## 3. Register the runtime with containerd

Add a Kata + Cloud Hypervisor runtime handler. With containerd's v2 runtime,
the handler name (`kata-clh`) maps to the `containerd-shim-kata-v2` shim, and
the config path selects the `clh` hypervisor:

```toml
# /etc/containerd/config.toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata-clh]
  runtime_type = "io.containerd.kata.v2"
  privileged_without_host_devices = true
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata-clh.options]
    ConfigPath = "/etc/kata-containers/configuration-clh.toml"
```

Restart containerd:

```bash
sudo systemctl restart containerd
```

## 4. Expose it as a Kubernetes RuntimeClass

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata-clh
handler: kata-clh # must match the containerd runtime handler above
```

```bash
kubectl apply -f runtimeclass-kata-clh.yaml
```

## 5. Run kirocrew inside a micro-VM

Set `runtimeClassName` on the kirocrew workload — nothing else about the
manifest changes:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kirocrew
  namespace: PLACEHOLDER # e.g. kirocrew
spec:
  replicas: 1
  selector:
    matchLabels: { app: kirocrew }
  template:
    metadata:
      labels: { app: kirocrew }
      annotations:
        # Give a busy agent more headroom without touching the global config.
        io.katacontainers.config.hypervisor.default_memory: '1024'
    spec:
      runtimeClassName: kata-clh
      containers:
        - name: agent
          image: PLACEHOLDER # your kirocrew agent image
```

Verify the pod is actually in a VM — it should report a **different kernel**
from the host:

```bash
uname -r                                   # host kernel
kubectl exec deploy/kirocrew -- uname -r   # guest kernel (should differ)
```

If those two differ, the agent is running in its own Cloud Hypervisor VM. 🎉

## What worked, what to watch

- **Boot time** — Cloud Hypervisor VMs start fast enough that per-pod isolation
  didn't noticeably hurt the agent's responsiveness.
- **Blast radius** — a compromised or misbehaving agent is now contained to its
  own kernel and VM, not the host.
- **Gotcha: nested virtualization** — on a cloud VM you need nested virt enabled
  (or a bare-metal/`*.metal` instance), otherwise `kata-runtime check` fails.
- **Gotcha: host volumes** — bind-mounting host paths into a Kata pod behaves
  differently than with runc (it goes through virtio-fs). Prefer proper volumes
  for anything the agent writes heavily.
- **Gotcha: annotations must be allowlisted** — per-pod resource overrides are
  ignored unless the matching keys are enabled in `configuration-clh.toml`.
